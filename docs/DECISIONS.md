# Project Atlas — Architecture Decision Record

Format: decision · why · alternatives rejected. Status: **Accepted** (revision 2, 2026-11-04) unless marked otherwise.

### ADR-001 Modular monolith
One FastAPI app with internal domain packages and one deploy unit. **Why:** a small team on a hackathon timeline; the transactional consistency we need (order + stock + outbox in one transaction) is trivial in one process. **Rejected:** microservices (distributed transactions with no benefit at this scale); serverless functions (cold starts, no shared transactions, harder webhook handling).

### ADR-002 Managed PostgreSQL when deployed, SQLite locally (revised)
The deployed database is a **free managed PostgreSQL** instance (Neon free tier). Local development and the fast test suite can use SQLite. The app **refuses to start in production with SQLite**. Access goes through SQLAlchemy 2 (sync) with the psycopg 3 driver, and migrations go through Alembic. CI runs the backend tests against both databases. **Why:** the Render free web service has an ephemeral filesystem and no persistent disk, and the user has ruled out paid plans. An external managed database survives restarts, redeploys and sleep. Neon's free tier doesn't expire; it suspends idle compute, which we handle with `pool_pre_ping`. **Rejected:** a Render persistent disk (requires a paid plan); Render free PostgreSQL (time-limited free instances); Supabase free (inactive projects are paused); SQLite on the Render free filesystem (data lost on every deploy or restart); PostgreSQL only, including locally (Docker isn't available on the dev machine, and SQLite keeps local tests fast; the CI matrix covers drift).

### ADR-003 Money as integer minor units; USD is the single store currency (revised)
Every price, total and PayPal amount is in **USD**, stored as cents. The UI formats amounts with `Intl.NumberFormat` in the user's locale but never converts them. **Why:** what PayPal charges must be exactly what was shown; USD works for an international Sandbox buyer; one currency removes a class of mismatch bugs. **Rejected:** live FX display (a guessed price); per-currency price lists (out of scope, although the `currency` column keeps the option open); EUR or BRL as the store currency; INR (see ADR-019).

### ADR-004 "AI proposes, backend decides" pipeline
Extract intent (validated JSON) → deterministic services → LLM composes text from structured, placeholder-protected results → validators. Prices and stock reach the UI only through structured fields. **Why:** this makes "no AI-generated prices, stock, payment state or order IDs" a structural guarantee that tests can check, instead of a prompt request. **Rejected:** a free-form agent with tool calls that mutate state (hard to bound, prompt-injection risk); letting the LLM write prices in prose (unverifiable).

### ADR-005 Provider-agnostic LLM runtime; Gemini 3.8 Flash initially (revised)
A `LLMProvider` protocol with `generate_structured(messages, schema)` and `generate_text(messages)`. The first adapter is **Gemini**, with **`gemini-3.8-flash`** as the default model. Provider and model come from env (`LLM_PROVIDER`, `LLM_MODEL`, `GEMINI_API_KEY`), so changing either needs no code change. A deterministic fake adapter serves tests and offline development. The vendor SDK is imported only inside its adapter. **Why:** a locked requirement; CI stays independent of the network and of cost; the audit found that vendor coupling in domain code was the main problem in Raahat and Athena. **Rejected:** LangChain-style frameworks (a heavy abstraction for two calls per turn); a hard-coded multi-vendor fallback chain (Athena's pattern); calling the SDK from domain code.

### ADR-006 Full-text retrieval behind one interface; semantic deferred (revised)
A `KnowledgeIndex` interface with two implementations:
- **PostgreSQL** (deployed): a `tsvector` column with a GIN index. Each chunk uses its language's built-in text-search configuration (`english`, `spanish`, `french`, `german`, `portuguese`), queried with `websearch_to_tsquery` and ranked with `ts_rank_cd`.
- **SQLite FTS5** (local and tests): tokenizer `unicode61 remove_diacritics 2`.

Both implementations must pass the same retrieval contract tests and evaluation set. When the target language has no documents, the query is translated to the merchant's source language. **Why:** the corpus is small and keyword-heavy. PostgreSQL's per-language stemming is a real advantage for es/fr/de/pt. No new infrastructure is needed. **Rejected:** a vector database or `pgvector` embeddings (not justified until the evaluation set shows recall failures); FTS5 only (not available in PostgreSQL); stuffing the whole corpus into the prompt.

### ADR-007 PayPal Orders v2: server-side create and capture, JS SDK for payer approval
`createOrder` and `onApprove` call our backend, and the backend calls PayPal with `PayPal-Request-Id`. Payment is confirmed by the capture response, and signature-verified webhooks reconcile it. **Why:** the server controls amounts, so the client can't tamper with them; capture is idempotent; webhooks cover async or pending cases. **Rejected:** client-side `actions.order.capture()` (the browser becomes a payment authority); webhook-only confirmation (slow, and fragile while a free instance is waking); other gateways.

### ADR-008 Explicit approval through a versioned order snapshot
"Review" creates an immutable snapshot with a `version_hash`. Approval must present that hash, and PayPal order creation is allowed only from `approved`. Changing the presentation language doesn't alter the snapshot or its hash. **Rejected:** approval through a chat message (ambiguous, injectable); recomputing totals at capture time.

### ADR-009 Inventory: reserve at approval, commit at capture, release on expiry or failure
**Why:** prevents overselling between approval and capture without locking stock for browsing carts. **Rejected:** decrementing at add-to-cart; decrementing only at capture. A residual conflict, where a capture completes after the reservation expired and stock is gone, becomes an exception and is never handled silently.
**Amended (M3.1, ADR-025):** stock is reserved once, by the cart's reservation (ADR-024), and an order **adopts** that reservation instead of reserving again. The hold is protected from then on: it ends only through the order (committed by a verified capture, released by cancellation or a definitive, PayPal-confirmed failure, or expired before capture). A capture can only start while the hold is safely within its deadline (M3.2), so the residual conflict above can't arise from Atlas's own flow; a completed capture found on an order that has already ended is flagged `needs_review` with no automatic stock change. There is no general exceptions table in M3: order statuses and payment records carry this.

### ADR-010 Make via a database-backed transactional outbox (revised)
Events are written in the same transaction as the state change. The dispatcher claims them with a crash-safe lease (a conditional `UPDATE`, which works on both databases). Delivery carries an HMAC signature, an API key and a stable `event_id` as the idempotency key. Retries use exponential backoff with jitter, up to `max_attempts`. Events that exhaust their attempts become `dead` and raise an exception. The dashboard shows every attempt and offers manual retry. On startup the dispatcher resumes pending events and events whose lease expired. Delivery is at-least-once; the Make Data Store dedup on `event_id` makes the effect exactly-once. Make callbacks are informational and append-only. **Why:** Make downtime, a crash or free-tier sleep never loses an event or affects checkout. **Rejected:** synchronous Make calls in the request path; Make as a store of state; a Redis or Celery queue (infrastructure without a measured need); an in-memory queue (lost on restart).

### ADR-011 Language, locale, currency and destination are separate fields
**Why:** a Portuguese speaker in Germany shipping to France and paying in USD is a normal customer. **Rejected:** deriving any one of these from another.

### ADR-012 Single Render free web service, Docker runtime (revised)
A multi-stage Dockerfile builds the Vite app with Node, then runs FastAPI on Python 3.11, serving `/api/*` and the SPA from one origin. `scripts/start.sh` runs `alembic upgrade head` before uvicorn. `render.yaml` declares `plan: free`. **Why:** same origin (no CORS, simple cookies); one stable URL for PayPal webhooks; a reproducible build that CI can test without Render; no paid features required. **Rejected:** a separate static site plus API (CORS and cookies); Render's native Python runtime (Node availability for the SPA build is less predictable); pre-deploy commands (not relied upon on the free plan); any paid Render plan (excluded by the user).

### ADR-013 Merchant auth: single admin credential from env
**Why:** single-merchant scope; this is honest about being a hackathon-grade control. **Rejected:** OAuth or an identity provider. Documented as a production gap.

### ADR-014 In-process background workers, state in the database
Asyncio loops are started in the FastAPI lifespan: outbox dispatcher and reservation expiry. All their state lives in the database, so a restart loses nothing (ADR-010). Reservation expiry also runs lazily on reads, so expired reservations don't keep holding stock while the instance is asleep. **Rejected:** Celery or RQ with Redis.
**Amended in M2 by ADR-024 (D6):** reservation expiry has **no** background loop; it is lazy only. The outbox dispatcher (M4) remains the planned in-process loop.

### ADR-015 Catalogue and knowledge translations are stored, not generated live
Translations live in `product_translations` and per-language knowledge docs. A seed-time script may draft them with the LLM. Those drafts are flagged `machine_translated`, pass placeholder validation (ADR-018) and are committed for review. **Rejected:** translating catalogue text live on every request.

### ADR-016 Existing multilingual codebases: audited, patterns adapted
Audit complete ([MULTILINGUAL_REUSE_AUDIT.md](MULTILINGUAL_REUSE_AUDIT.md)). No domain code is ported. Patterns that are adapted: immutable original text, the translation preservation check, closed-enum extraction, a language preference with safe storage, and translation-table integrity tests. Generic helpers from the MIT-licensed Second Look may be reused with attribution. **Rejected:** script-based detection, the existing dictionaries, Athena's embedding/OCR/voice stack.

### ADR-017 Language detection and resolution policy (new)
Detection is statistical character n-gram language identification restricted to `en/es/fr/de/pt`, run on text with URLs, SKUs, numbers and emoji removed. It returns `undetermined` for short or low-confidence input. There is **no alphabet or script-based detection** for these languages. Resolution precedence: **explicit user selection > conversation language > confident detected switch > UI locale > en**. A switch needs a confidence threshold and a minimum word count, both tuned on the Atlas evaluation set. Manual switching is always available, and Auto restores detection. Every decision is recorded with its source. **Why:** all five initial languages share the Latin script; short replies and product names must not flip the conversation; a user's explicit choice must be respected. **Rejected:** script heuristics; keyword lists; LLM-only detection (adds latency and isn't deterministic, although the model's reported language may be logged for evaluation); per-message switching with no stickiness.

### ADR-018 Protected-placeholder validation (new)
Product IDs, SKUs, sizes, quantities, URLs, numeric values and monetary amounts are replaced with typed tokens before any model composition or translation. The output must keep a valid token set: equal to the input's for translation, a subset for composition, with no invented tokens. After the tokens are removed, it must contain no digits, currency markers, URLs or SKU-shaped strings. Values are substituted only at render time from structured data. Failure leads to one retry, then a template reply. **Why:** generalises Raahat's `_preserved()` check into a guarantee that translation can't alter commercial or payment data, in any number format. **Rejected:** regex checks on numbers in the final text (fail on European formats such as `1.299,00`); trusting prompt instructions alone.

### ADR-019 PayPal demonstration scope (new)
The demo uses **PayPal Sandbox only**: a Sandbox business (merchant) account and a Sandbox personal account acting as an **international buyer**, checking out in **USD**. We make no claim about domestic Indian PayPal payments, INR checkout or live payments. **Why:** PayPal's support for domestic payments between Indian accounts is restricted, and the product targets cross-border sellers. Stating the scope prevents an overclaim during judging. **Rejected:** INR pricing; presenting Sandbox as production readiness.

### ADR-020 Make connected apps: Google Sheets, Gmail, Telegram (new)
Sheets is the order, stock and exception log. Gmail sends customer confirmation emails. Telegram, via a bot, carries merchant alerts. Everything runs through one webhook-triggered scenario with a router by event type. **Why:** all three are free to use, quick to show in a demo, and cover the merchant-log, customer and merchant-alert channels. One scenario stays within Free-plan limits. **Rejected:** Slack and SMTP (excluded by the user); one scenario per event type (uses more of the active-scenario allowance and needs more webhook URLs to manage).

### ADR-021 Portable catalogue search for M1 (new, M1)
Catalogue search normalises text (case-fold, accents removed, punctuation collapsed) and stores it per translation. A query's words (at least 2 characters, at most 8 words) must all match a word start via `LIKE '% term%'`. Name matches score 2 and description matches score 1, using portable `CASE` expressions. English text is always searchable. Every ordering ends with product id. **Why:** about 100 translation rows; identical results and ordering on SQLite and PostgreSQL; no new infrastructure. **Known limitation:** no stemming ("jacket" matches "jackets" by prefix, but "chaquetas" does not match "chaqueta"). **Rejected for M1:** PostgreSQL `tsvector` with SQLite FTS5 (dialect-specific ranking makes results differ between databases); vector search. Revisit alongside ADR-006 in M6 if evaluation shows recall problems.

### ADR-022 Opt-in, create-only seeding at startup (new, M1)
`scripts/start.sh` runs migrations, then `python -m app.seed` only when `SEED_CATALOG_ON_START=1`, then the server. `set -e` stops startup at the first failure. The seed validates both files before connecting, refuses to run unless the schema is at the migration head, runs in one transaction, creates only missing rows, never deletes, and never writes stock to an existing variant: starting stock is set once, with an `initial_stock` movement. Differences between the files and the database are reported as drift. `--update` (local use only) refreshes descriptive fields and prices but never stock. **Why:** Render's free plan has no shell, and the demo catalogue must reach production safely. **Rejected:** data migrations (tie demo data to the schema); manual seeding from a laptop against production (credential handling).

### ADR-023 Fictional shipping origin: India (new, M1)
The demo merchant, "Atlas Demo Outfitters" (a temporary name), is fictional and ships from India to four international zones at flat USD rates. These rates are **demo pricing assumptions, not real or carrier-validated shipping costs**. India itself is not a destination. This is story data only. It **does not** change ADR-019 or make any claim about PayPal merchant-account capabilities. The PayPal Sandbox merchant-account country (D-12) is deferred to M3.

### ADR-024 Cart-owned stock reservations with lazy expiry (new, M2)
In M2 a reservation belongs to a cart; orders, order snapshots and customer approval arrive in M3 (D1). A customer explicitly reserves their cart, which holds stock for `RESERVATION_TTL_MINUTES` (15 by default, no renewal, D3). A reservation records only which variants and quantities it holds, and the cart version it was made for. **It carries no prices:** carts and reservations show live catalogue prices, and the price snapshot belongs to the M3 order. Any cart change releases the active reservation in the same transaction (D2). Limits: 10 units per line and 20 lines (D4). Carts are anonymous: an opaque random token in an httpOnly cookie, stored only as a SHA-256 hash, so no session secret is needed. A cart expires 30 days after its last change (D8). Reservation movements use three reasons, `reservation_hold`, `reservation_release` and `reservation_expiry`. They may move only reserved stock and must name their reservation through `inventory_movements.reservation_id`; stock adjustments must not. Sale and commit reasons arrive with M3 (D5). Reservations, their items and their movements are audit history and are never deleted.

**Service contract (binding on M2.2; amended before implementation).** It assumes PostgreSQL's default READ COMMITTED isolation.
- **Global lock order: cart row → reservation row → variant rows in ascending `variant_id`.** The expiry sweep is the only exception: it never locks a cart.
1. **Cart edits.** Every cart edit advances `carts.version`, which takes the cart row lock. Only then does it look up and end any active reservation, in the same transaction. Looking it up after the version update means a reservation committed while the edit waited for the lock is seen.
2. **Repeated reservation requests.** A reservation request reads the cart version and the active reservation in **one SQL statement**. If the reservation is active, **unexpired** and made for the current version, it is returned unchanged.
3. **The cart's own overdue reservation** is expired in its own short transaction **before** the main reservation transaction, never inside it (doing so would lock the reservation before the cart).
4. **New reservations.** Otherwise it advances the cart version with an atomic compare-and-set and creates a reservation for the new version. The version change, stock holds, reservation, items and movements commit together; if any variant can't be held, all of it rolls back.
5. **Lost races.** If the compare-and-set loses a race, it re-reads the cart and reservation. It returns the matching active, unexpired reservation if another request created it; otherwise it returns a conflict.
6. **Fresh reads.** Cart edits, reservation creation and customer release serialise on the cart row. Cart contents and the active reservation are re-read after acquiring the lock or version update; a stale pre-lock snapshot is never reserved. Values written by raw SQL updates are read back with `RETURNING` or `populate_existing()`.
7. **Ending a reservation is a compare-and-set.** Expiry is `status = 'active' AND expires_at <= :now`; customer release is `status = 'active'`, after taking the cart lock. A release of an overdue reservation is recorded as `reservation_expiry`. The successful transition and its stock release happen in **one transaction**. If the compare-and-set affects zero rows, stock is not released again; a release with nothing active is a successful no-op.
8. **Sweeps run separately.** Overdue reservations of *other* carts are swept **before** the current cart's lock is acquired, one reservation per short transaction, never while holding a cart lock.
9. **Release quantities.** Reservation item quantities are immutable snapshots used for release, never recomputed from the current cart. Holds require an active variant and product; releases don't, so archived stock is always released.
10. **Advisory availability.** Setting a cart quantity checks availability without holding stock and never reports counts (D-5). Only a reservation holds stock.

See ARCHITECTURE §3.1.

**Expiry is lazy (D6).** There is no always-running worker. An expired reservation is expired and released when the cart or reservation is next read or changed, and before any new reservation, for the variants it needs. Expiry decisions are made in SQL against a UTC time from an injectable clock. **Limitation:** until someone touches it, an expired reservation keeps its stock counted as reserved, so other customers can briefly see it as unavailable. A bounded sweeper (for example on startup, or for at most N overdue reservations per request) can be added if the demo shows this. **Why:** correctness doesn't depend on a background loop, which a sleeping free instance pauses anyway. **Rejected:** reserving at add-to-cart (idle carts lock stock); locking the cart while reserved; an in-process expiry loop in M2.

### ADR-025 Orders adopt the cart's reservation; the order owns the hold (new, M3.1)
Creating an order (`POST /api/cart/orders`) requires an active, unexpired reservation made for the cart's current version. In one transaction it takes the cart lock, re-reads the reservation and lines (they must match, and every item must still be available), quotes shipping, and writes an immutable snapshot: the order and its items in integer USD cents, with a canonical SHA-256 `version_hash` over the reference, currency, destination, lines and totals (names and language are excluded, ADR-008). It then moves the reservation `active → order_hold` with a compare-and-set. **No stock is reserved again and no movement is written;** the order gets a new hold deadline, `ORDER_HOLD_MINUTES` (30 by default, 15–60) from creation.

**The order owns the hold.** Every cart-side expiry, release and sweep matches only `status = 'active'`, so none can end an `order_hold`. While a cart has an open order, every cart write (set quantity, remove line, reserve, release) is refused with `checkout_in_progress` (the order's reference in `details`), checked after the cart lock. A hold ends only through its order:
- before capture (`pending_approval`, `approved`, `awaiting_payment`): the customer cancels (`order_hold → released`), or the deadline passes (`→ expired`, applied lazily when the order or bag is read, before a cart change, and by other carts' bounded sweeps of the same variants);
- while a payment may exist (`capturing`, `payment_pending`, `needs_review`; M3.2): neither cancellation nor expiry applies, and stock stays held;
- a verified completed capture commits it (`→ committed`, a `sale` movement lowering on-hand and reserved stock by the same quantity; the primitive exists and is tested in M3.1, used from M3.2); only a definitive, PayPal-confirmed failure releases it.

Invariant: `stock_reserved = SUM(items of active + order_hold reservations)`. Lock order: cart → order → reservation → variants (ascending); cancellation and expiry skip the cart, like the reservation sweep. No transaction or lock is held across a network call.

**Ownership and recovery.** Orders are read and cancelled only through the cart that owns them: the lookup is by public reference **and** the `atlas_cart` cookie's cart, so another cart's reference is `order_not_found`. Order routes live under `/api/cart/orders` because the cookie is scoped to `Path=/api/cart`, which also gives them `no-store`; widening the cookie's path was rejected. Repeating the create request returns the cart's open order (200), and `GET /api/cart` reports it as `checkout`, so a client that timed out after the first request committed can recover the reference. A cart has at most one open order (partial unique index) and a reservation at most one order.

**Rejected:** reserving again at order creation (double holds, a second shortfall path); letting the cart TTL end an order's hold (a customer in the PayPal window could lose stock mid-payment); finding orders by reference alone; a general exceptions table in M3.

### ADR-026 PayPal Sandbox payments: verified capture, one finalization, ambiguity keeps the hold (new, M3.2)
**Sandbox only.** The API host `https://api-m.sandbox.paypal.com` is a constant in code, with no base-URL setting. Payments are enabled only when `PAYPAL_MODE` is exactly `sandbox` and the client id, client secret and Sandbox merchant id are all set; otherwise the three payment endpoints answer 503 and the shop keeps working. Server-side OAuth client credentials; Orders v2 create (`intent: CAPTURE`, USD, items and breakdown from the immutable snapshot, `invoice_id` = `custom_id` = `reference_id` = the Atlas order reference, `payee.merchant_id`) and capture; Payments v2 *show capture* as the authority.

**Paid means PayPal's own capture record shows** `COMPLETED`, the stored PayPal order (`related_ids.order_id`), our reference as `invoice_id`, our merchant as `payee.merchant_id` (a missing merchant id fails closed), USD, and exactly the snapshot total in integer cents. The browser only identifies the order and forwards PayPal's order id, which must equal the stored one; redirects and client callbacks prove nothing. `PENDING` is not paid.

**Ambiguity keeps the hold.** Timeouts, connection failures, 5xx and unrecognised errors are never failures: the order stays `capturing` or `payment_pending` with its `order_hold`, and is reconciled against PayPal's order before anything else happens. Only definitive PayPal evidence releases stock: a capture record `DECLINED` or `FAILED` (with no other successful or pending capture on the order), or a `VOIDED` PayPal order. `INSTRUMENT_DECLINED` is a recoverable Orders API error, not a capture status: no capture exists, the order returns to `awaiting_payment` with the hold, and the client gets the recoverable result `instrument_declined` (the frontend calls `actions.restart()`, M3.4). Unresolved after 72 hours: `needs_review`, hold kept.

**Idempotency and crash recovery.** One PayPal order per Atlas order (its id written once by compare-and-set). The create request id is stored at approval; the capture attempt number, request id and start time are stored by the capture claim **before** PayPal is called. A request that finds a stale `capturing` order (older than `STALE_CAPTURE_AFTER`, longer than any live request) reconciles first and, only if PayPal shows the order approved with no capture, retries the same logical request with the **same** `PayPal-Request-Id`. A new attempt id is used only after a recoverable funding failure. No transaction or row lock is held during a PayPal call.

**One finalization.** Capture responses, explicit reconciliation, the merchant command and M3.3's webhooks all call `finalize`, which in one transaction (cart → order → reservation → variants) records the evidence (unique per capture and status) and applies the outcome once: `paid` with the reservation `committed`, `sale` movements and the bag emptied; or `payment_pending`, `payment_failed` (hold released) or `needs_review` (hold kept). A verified completed capture for an order that has already ended is recorded and marked `needs_review` (`capture_after_end`) with no stock change and no fulfilment; if the cart already has another open order, the reason is recorded on the ended order and the merchant command lists it.

**Data minimisation.** `payments` keeps only verification and reconciliation fields (capture id, status and reason, amount, currency, invoice id, related order id, merchant id, source, PayPal debug id): no raw bodies, no payer names, emails, addresses or payer ids. Logs carry the order reference, PayPal issue codes and debug ids only.

**Rejected:** trusting the capture response alone (the capture object's fields aren't guaranteed to carry the merchant or reference); treating timeouts as failures; retrying a capture with a new request id after an ambiguous result; reconciling as a side effect of `GET`; storing raw PayPal responses; a configurable API base URL. Webhook verification and event persistence are M3.3 (migration `0006`).
